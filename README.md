# Starter repository

Те, що студент клонує на першому уроці й дороблює до capstone.

**➡ Повний гайд для студента (вимоги, запуск, кожна папка, troubleshooting): [GETTING_STARTED.md](GETTING_STARTED.md).**
**➡ Домашні завдання — окремий файл на кожен тиждень: [homework/](homework/README.md).**

## Що дається готовим, що добудовує студент

| Компонент | Дається готовим | Студент добудовує |
|---|---|---|
| UI (Angular) | готові в'юхи: Chat + Console/Observability | не змінює |
| App service (.NET) | skeleton | control plane: routing, fallback, cost, policies |
| Observability API (.NET) | skeleton | агрегати з Postgres (traces, p95, cost, error-taxonomy) у Console-в'юху |
| Gateway (LiteLLM) | базовий конфіг | моделі/провайдери, порядок fallback |
| Mock provider | готовий | використовує для тестів і failure-сценаріїв |
| Postgres | базова схема | розширює під logs / cost / prompt records |
| Eval runner (Python) | skeleton | dataset, graders, пороги |
| CI (GitHub Actions) | шаблон `.github/workflows/eval-gate.yml` | eval gate |
| Redis / дашборди | опційний шаблон | advanced extension |

## Запуск (мінімальний стек)

```sh
docker compose up --build
```

Піднімаються: UI (`:4200`), сервіс (`:8080`), LiteLLM (`:4000`), Postgres, mock provider.
Для mock реальні ключі не потрібні. Redis і дашборди — опційні: `docker compose --profile advanced up`.
Для оцінки якості (model-based evals): `cp gateway/.env.example gateway/.env` і заповнити ключі.

## Операційні рішення

Дублює опис PR для HW3 ([homework/hw3.md](homework/hw3.md), п.3), щоб перевірка не залежала від платформи.

**Timeout на tool-виклик: 2000 мс** (`TOOL_TIMEOUT_MS` у `docker-compose.yml`, код — `service/Tools.cs`).
Інструмент не повинен з'їсти бюджет усього запиту: `lookup_order` читає статус з пам'яті за мілісекунди,
тож 2 с — це запас, а не очікувана тривалість. Це **один бюджет на весь виклик інструмента**, а не на кожен
номер: кілька номерів (до 3, див. нижче) перевіряються паралельно під спільним таймаутом, тож три номери не
займуть утричі більше часу. Після таймауту `/chat` не падає: користувач отримує чисту відповідь «Не вдалося
перевірити статус замовлення вчасно…» (для кількох номерів — «не вдалося перевірити вчасно» біля кожного,
що не встиг) без вигаданого статусу, а в лозі — рядок `Timeout` з лімітом. Перевіряється юніт-тестом
`SlowTool_TimesOutWithinBudget` (`tests/`), бо `__delay` затримує виклик моделі, а не інструмент.

**Номер замовлення для `lookup_order`.** Спершу береться `order_id` з аргументів моделі, інакше — номер з
повідомлення користувача (mock завжди шле `arguments = "{}"`). Валідатор (`NormalizeOrderId`: ASCII-цифри, від 1 до
10) спільний для обох шляхів, а поверх нього діє **правило довжини**: число без позначки — номер замовлення лише до
6 цифр, довший номер — лише з позначкою (`#1234567`, `№1234567`). Правило однакове для тексту повідомлення і для
`order_id` з аргументів (див. нижче).

| Що в повідомленні | Що робить сервіс |
|---|---|
| `#123`, `＃123`, `№123`, `# 123` | номер 123: позначка `#`, повноширинна `＃` або `№`, пробіли після неї необов'язкові |
| `замовлення 123` (число без позначки, 1–6 цифр) | номер 123, **лише якщо це єдине число без позначки в повідомленні**, довгі (7+ цифр) теж рахуються. У «2 товари, замовлення 123» номер не вгадується — сервіс перепитує. Якщо є хоч один номер з позначкою, числа без позначки не враховуються |
| `мій номер 0671234567`, `1234567` (7 і більше цифр без позначки) | не номер: найімовірніше, це телефон. Його **не перевіряють і назад не повертають** — ні у відповідь, ні в лог. Довший номер замовлення — лише з позначкою: `#1234567`, `№1234567`. **Але довге число рахується як «ще одне число»:** у «Де замовлення? Доставка на Шевченка 123, тел. 0671234567» чи «Мій телефон (555) 1234567» чисел два, тож сервіс перепитує, а не перевіряє номер будинку чи код міста |
| `iPhone15`, `15шт`, `Хай15` (цифри, приліплені до літери будь-якої абетки, зокрема до літери з комбінованим знаком — розкладене «й») | не номер і не рахується як ще одне число, навіть довге. Діє лише для приліплених цифр: у «Купив iPhone 15» з пробілом 15 — звичайне число без позначки, і сервіс перевірить #15 |
| `#0123` | номер 123: провідні нулі відкидаються; `#0` чи `#000` — не номер |
| `#١٢٣`, `#１２３` | не номер: приймаються лише ASCII-цифри `0-9` |
| понад 10 цифр з позначкою (з провідними нулями включно) | не номер, і **назад не повертається** — ні у відповідь, ні в лог |
| `#555 і #123` | перевіряються обидва, кожен зі своїм статусом: « (статуси: #555 — очікує оплати; #123 — в дорозі, доставка завтра)». Повтори того самого номера (`#123 … #0123`) рахуються один раз |
| понад 3 різні номери | перевіряються перші 3 у порядку появи; решта лише рахується: «Інші номери замовлень (ще N) не перевірено: за один запит перевіряю щонайбільше 3.» Самі номери не перелічуються |

Один номер дає звичну форму « (статус: …)». Якщо жодного придатного номера немає, інструмент не викликається,
а користувач отримує «Вкажіть, будь ласка, номер замовлення (наприклад, #123 або №123).» — статус не вигадується.

> **`order_id` з аргументів моделі — те саме правило довжини.** До 6 цифр приймається як є. 7–10 цифр
> приймаються, **лише якщо користувач сам написав той самий номер з позначкою** («№0671234567»); позначка, яку
> поставила модель, не рахується. Інакше це, найпевніше, телефон, який модель витягла з тексту: сервіс вважає,
> що аргументу немає, — не перевіряє, не повертає у відповідь і не пише в лог — і шукає номер у повідомленні.
> Ціна рішення: довгий номер замовлення, написаний без позначки, не пройде й через модель — сервіс перепитає.
> Зараз цей шлях недосяжний: mock завжди шле `arguments = "{}"`, а сервіс не оголошує моделі інструментів.

> **Тихе значення за замовчуванням.** `TOOL_TIMEOUT_MS` і `CACHE_TTL_SECONDS`, що дорівнюють нулю, від'ємні
> або не є цілим числом, **без жодного повідомлення** замінюються на 2000 мс і 600 с. Тобто
> `CACHE_TTL_SECONDS=0` кеш **не вимикає**.

**Ключ ідемпотентності для side-effecting дій: `request_id`** (UUID, який сервіс генерує на кожен `/chat`
і пише в `requests`). Повтор дії всередині того самого запиту (наш власний ретрай або fallback на
іншу модель у W4) нестиме той самий `request_id`, тож дія з уже баченим ключем не має виконуватися
вдруге. Цю перевірку буде реалізовано в HW4, коли `create_ticket` почне виконуватися; зараз її в коді немає.
**Чесна межа:** `request_id` закриває лише наш власний ретрай у межах одного запиту. Повторне прохання
моделі наступним ходом чи подвійний клік користувача — це вже нові `request_id`; від них захищає лише ключ
від самої дії, `hash(conversation_id, tool_name, args)`, і він за межами core. У HW3 єдина
side-effecting дія, `create_ticket`, ще **не виконується** (лише показується її назва), тому рішення поки
що зафіксоване, а не перевірене: поведінкова перевірка — у HW4, разом із чергою approvals.

**Кеш відповідей: TTL 600 с** (`CACHE_TTL_SECONDS`, код — `service/ResponseCache.cs`). Ключ — SHA-256 від
моделі, версії промпта і всіх повідомлень, що йдуть у модель (системне повідомлення — це текст промпта), тож
відкат промпта чи інша модель дають промах, а не стару відповідь. Кеш живе в пам'яті сервісу, а не в Redis
(Redis є лише в профілі `advanced`), тому **очищується при кожному перезапуску** контейнера `service`. У кеш
потрапляють відповіді зі статусом 200, розпарсеним `usage` і непорожнім текстом; помилки gateway, вибачення
сервісу і `create_ticket` — ні. **Змісту відповіді кеш не перевіряє:** беззмістовна відповідь `"..."` (маркер
`__garbage`) приходить зі статусом 200 і теж кешується. Детектор такого браку (HW5) має стояти і перед
записом у кеш, інакше повтор віддасть `"..."` з кешу в обхід чесної гілки. Кешується вихід моделі, а не
фінальна відповідь: `lookup_order` виконується знову навіть на hit, тож статус замовлення не застаріває.

**Однакові одночасні запити — один виклик моделі (single-flight).** Якщо ідентичний запит (той самий ключ
кешу) приходить, поки перший ще чекає на модель, він у модель не йде, а чекає результат першого. Як його
рахувати, вирішує результат, а не саме очікування (`hits + misses` = кількість запитів):
- **виклик першого вдався** (200 і розпарсений `usage`) — це hit, у лозі
  `hit (waited for an identical in-flight request)`, у `requests` рядок 0 / 0 / 0, як у звичайного hit;
- **виклик першого не вдався** — це miss, у лозі
  `miss (waited for an identical in-flight request that failed)`. Збій отримують усі, хто чекав,
  **без повтору**, а їхні рядки — зі статусом першого і `cost_usd = NULL`, щоб збій не порахувався як hit (W5).
  503 на 20 однакових запитів дає 0 hits і 20 misses.

Токени й вартість у `requests` пише лише перший запит. У кеш збій не потрапляє, тож наступний запит після
нього знову піде в модель. Інструмент single-flight не об'єднує: `lookup_order` виконується на кожному запиті
окремо.
