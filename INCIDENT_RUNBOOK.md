# INCIDENT_RUNBOOK: провайдер моделі лежить → fallback → відновлення

Інцидент-демо HW6 ([homework/hw6.md](homework/hw6.md), п.3). Посилання на цей файл є в
[README](README.md#hw6-ci-гейт-і-інцидент). Сценарій відтворює на mock-стенді те, що
бачить черговий, коли провайдер моделі віддає `503`: ланцюжок fallback вичерпується,
користувач отримує чесну заглушку замість помилки, запобіжники відкриваються, консоль
червоніє. Після паузи нове питання знову отримує нормальну відповідь, і консоль
показує відновлення.

- **Реальний ключ не потрібен:** збій вмикає маркер `__fail_503` у тексті повідомлення,
  mock відповідає на нього `503`.
- **Скільки часу:** близько двох хвилин.
- **Що знищується:** нічого. Рядки в `requests` лишаються. Перезапуск `service` у кроці 0
  обнуляє лише стан у пам'яті сервісу (кеш, запобіжники, `fallback_events`, черга HITL).
- **Команди виконуються дослівно**, у тому порядку, в якому вони записані. Єдина дозволена
  правка — підстановка зсунутого порту (таблиця нижче).

| Що доводить демо | Де видно |
|---|---|
| fallback: сервіс пройшов ланцюжок `mock-mini → mock-mid`, а користувач отримав заглушку (HTTP 200), а не помилку | відповідь `/chat` у кроці 3, лог у кроці 4 |
| сплеск `fallback_events` | плитка «Fallback», `GET /observability` |
| зростання, потім спад `error_rate_pct` | плитка «Error rate», `GET /observability` |
| відкриті запобіжники і червона картка провайдерів, потім знову зелена | `circuits`, `GET /providers`, картка провайдерів |
| відновлення відповідає модель, а не кеш | `prompt_tokens > 0` у рядку `requests` (крок 7) |

## Перед стартом

**Стек піднятий:** `docker compose up --build -d`, і з моменту старту минуло щонайменше
30 с (холодний LiteLLM відповідає `500` на перший запит; крок 1 це перевіряє). Консоль —
<http://localhost:4200>, оновлюється кожні 4 с.

**Оболонка — bash:** Linux, macOS, WSL або Git Bash на Windows. Команди використовують
`curl`, `$(date +%s)`, `until`/`for` і `sleep`. PowerShell цей runbook не підтримує:
лапки JSON там пишуться інакше, і дослівно команди не виконаються.

**Зсунуті порти.** Якщо стек піднято з `demo-ports.yml`
(`docker compose -f docker-compose.yml -f demo-ports.yml up --build -d`), замініть у командах
`curl` порти за таблицею. Це єдина дозволена правка. Команди `docker compose restart`,
`logs` і `exec` звертаються до контейнерів проєкту, а не до портів хоста, тож лишаються
як є.

| Що | Стандартний порт | `demo-ports.yml` |
|---|---|---|
| сервіс | `8080` | `8180` |
| gateway | `4000` | `4100` |
| консоль (UI) | `4200` | `4300` |

## Крок 0. Чистий старт сервісу

```bash
docker compose restart service
```

```bash
until curl -sf http://localhost:8080/health > /dev/null; do sleep 1; done; echo ready
```

Очікується: `ready` через кілька секунд.

**Навіщо перезапуск:** він обнуляє все, що демо міряє в пам'яті. `fallback_events` стає `0`,
усі запобіжники — `closed`, кеш відповідей порожній. Без цього кроку числа нижче залежали б
від того, що робили зі стеком до вас. **Чому не `docker compose down -v`:** він стирає базу,
тобто всі рядки `requests` і реєстр промптів того, хто запускає runbook. Демо цього не
потребує.

> **Перезапуск мовчки губить чергу HITL.** Заявки `pending` живуть у пам'яті сервісу, тож
> після кроку 0 картка Approvals порожня. Для демо це не важить, але не запускайте runbook
> посеред перевірки заявок.

## Крок 1. Передумови

Gateway прогрітий:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:4000/v1/chat/completions -H "Content-Type: application/json" -d '{"model":"mock","messages":[{"role":"user","content":"ping"}]}'
```

Очікується: `200`. Якщо `500` чи `000`, зачекайте 10 с і повторіть. Цей запит іде в gateway
напряму, повз сервіс, тож лічильники демо не змінює.

Активний промпт — `v2`:

```bash
curl -s http://localhost:8080/prompts
```

Очікується: у записі з `"version":"v2"` стоїть `"active":true`. Якщо активний `v1` (наприклад,
після репетиції червоного гейта), поверніть `v2` і перевірте ще раз:

```bash
curl -s -X POST http://localhost:8080/prompts/v2/activate -H 'Content-Type: application/json' -d '{"activated_by":"incident-runbook"}'
```

**Чому це важливо:** з `v1` промпт не містить слова `support`, і mock на звичайне питання
відповідає «не знаю». Тоді крок 6 виглядав би як невдале відновлення, хоча провайдер
здоровий.

## Крок 3. Інцидент: провайдер віддає 503

Три звичайні питання, кожне з маркером збою. Текст навмисно англійською (пояснення в кроці 6):

```bash
for i in 1 2 3; do curl -s -X POST http://localhost:8080/chat -H 'Content-Type: application/json' -d '{"message":"__fail_503 I cannot login"}'; echo; done
```

Очікується: три відповіді HTTP 200, у кожній `"content"` — заглушка «Вибачте, зараз у нас
тимчасові технічні труднощі. Спробуйте, будь ласка, ще раз за кілька хвилин.», `"tool":null`.

Що відбулося всередині. Питання про вхід `Route()` веде на `mock-mini`. Його ланцюжок —
`mock-mini → mock-mid`. На `__fail_503` mock відповідає `503` будь-якому аліасу, тож кожне
питання падає на обох кроках:

- одне перемикання на питання — `fallback_events` +1;
- після вичерпаного ланцюжка — заглушка;
- у `requests` — рядок `mock-mini | 503` з `NULL` у токенах.

Третій збій поспіль відкриває запобіжники і `mock-mini`, і `mock-mid`.

> **Fallback тут видно як заглушку, а не як успішну відповідь запасної моделі.** Усі
> mock-аліаси — один провайдер, тож на `__fail_503` падає кожен крок ланцюжка. Що
> перемикання `503 → 200` справді віддає відповідь запасної моделі, перевіряють юніт-тести
> (`tests/FallbackTests.cs`), а не цей runbook. Пояснення — у README,
> [HW4 (надійність)](README.md#hw4-надійність-fallback-і-graceful-degradation).

## Крок 4. Що видно під час інциденту

```bash
curl -s http://localhost:8080/observability
```

Очікується:

- `"fallback_events":3`;
- `"circuits":{"mock-mid":"open","mock-mini":"open","mock-strong":"closed"}`;
- `error_rate_pct` вище за E0 (якщо E0 не було вже `100.0`). **Запишіть його:** це E1, пік.

```bash
curl -s http://localhost:8080/providers
```

Очікується: `mock-mini` і `mock-mid` — `"down"`, `mock-strong` — `"degraded"`. `mock-strong` ніхто
не кликав, але він стоїть на тому самому бекенді, що впав, тож зеленим не лишається.

У консолі <http://localhost:4200>: плитка «Fallback» — `3`, «Error rate» зросла, у картці
провайдерів три червоні точки.

```bash
docker compose logs --since 3m service | grep -E "fallback|degraded|circuit"
```

Очікується серед рядків:

- `fallback mock-mini -> mock-mid after 503` — тричі;
- `model call degraded after 1 fallback(s), last status 503` — тричі;
- `circuit mock-mini opened after 3 consecutive failures (last status 503)`;
- `circuit mock-mid opened after 3 consecutive failures (last status 503)`.

`grep` зачепить і стартовий рядок `MODEL=mock, fallback chains: …`, по одному на кожен старт
сервісу за ці 3 хв: до інциденту він не стосується.

**Повторний прогін з кроку 3 дає інші числа, і це не збій.** Без кроку 0 лічильник не
обнуляється, тож `fallback_events` зростає на 3, а не дорівнює 3. Вікно `--since 3m` захоплює й
попередній прогін, якщо він був менш ніж 3 хв тому: тут рядків буде вдвічі більше (6, 6, 2, 2), і
в кроці 7 рядків проби теж удвічі більше.

## Крок 5. Пауза

```bash
sleep 6
```

Відкритий запобіжник пропускає модель без виклику 5 с. Після цього перший запит до моделі
стає її пробою (half-open). **Закриває запобіжник лише вдала проба, а не таймер:** без
запиту модель лишається `open` скільки завгодно.

## Крок 6. Відновлення: нове питання

Контрольне питання — **нове**, з міткою часу в тексті. Його ще немає в кеші, тож відповідь
дає модель, а не кеш. Обидва питання цього кроку навмисно англійською (пояснення нижче):

```bash
curl -s -X POST http://localhost:8080/chat -H 'Content-Type: application/json' -d "{\"message\":\"I cannot login. Check $(date +%s)\"}"; echo
```

Очікується: `"content"` — «Щоб скинути пароль: відкрийте сторінку входу, натисніть «Забули
пароль» і перевірте email.», `"tool":null`. Цей запит став пробою `mock-mini`, проба вдалась, і
запобіжник `mock-mini` закрився.

Питання про замовлення, теж нове:

```bash
curl -s -X POST http://localhost:8080/chat -H 'Content-Type: application/json' -d "{\"message\":\"Where is my order #123? Check $(date +%s)\"}"; echo
```

Очікується: `"content"` закінчується на « (статус: в дорозі, доставка завтра)», `"tool":"lookup_order"`.

**Навіщо друге питання.** Звичайні питання йдуть на `mock-mini`, а він уже відповідає, тож
до `mock-mid` ланцюжок не доходить, і його запобіжник ніхто не пробує. Закрити `mock-mid`
може лише запит, який `Route()` веде на нього, тобто питання про замовлення. Без цього
кроку картка провайдерів лишилась би червоною назавжди (README,
[`GET /providers`](README.md#get-providers-статус-зі-стану-circuit-breaker)).

**Чому ці два питання англійською.** У Git Bash на Windows кирилиця в аргументах `curl`
перетворюється на `?` ([GETTING_STARTED.md, «Troubleshooting»](GETTING_STARTED.md#8-troubleshooting)).
Без слова `пароль` mock відповів би «Уточніть, будь ласка, деталі…», і це хоча б помітно.
**Друге питання зламалось би мовчки:** без слова `замовлення` `Route()` повів би його на
`mock-mini`, а mock усе одно впізнав би `#`, тож відповідь виглядала б правильною. Але `mock-mid`
не отримав би проби й лишився б `open`, а повтор запиту дав би той самий результат. Слова `login`
і `order` доходять цілими на будь-якій оболонці, а відповіді mock такі самі, як на українські
питання.

Крок 3 теж англійською, хоча збій там вмикає `__fail_503`, а цей маркер кирилицю не містить.
`?` — лише один вигляд втрати: якщо оболонка надішле байти, що не є коректним UTF-8, сервіс може
відхилити все тіло запиту, і заглушки не буде (виведено, на Windows не перевірено). ASCII у всьому
тексті прибирає цю залежність. Сам зміст питання там нічого не вирішує: без маркерів `Route()` і так
веде його на `mock-mini`.

**Навіщо мітка часу.** Кеш живе 600 с, і відповідь з кешу запобіжника не торкається:
вона закрила б демо «зеленим» без жодного виклику моделі. Крок 0 і так спорожнює кеш, а
`$(date +%s)` захищає ще й повторний прогін, що починається одразу з кроку 3. Мітка — лише
цифри: `#` у ній повів би перше питання в пошук замовлення.

**Міняючи текст кроку 6, збережіть `login` у першому питанні й `order` у другому.** Mock перевіряє
гілки по черзі, і відповідь дає перша, що спрацювала:

| Питання | Чого не може містити | Що станеться |
|---|---|---|
| обидва | `refund`, `поверн`, `терміново` | `create_ticket` замість очікуваної відповіді |
| перше | `order`, `замовлен`, `#` | `lookup_order` замість відповіді про пароль |

Слова з гілок після `login`, наприклад `hi` чи `допомог`, нічого не змінюють: ці гілки вже не
виконуються. **`Route()` має власний список, і помилка в ньому мовчазна:** `urgent` чи `delivery` не
змінять відповідь mock, але поведуть питання на іншу модель, і запобіжник потрібної моделі не
отримає проби.

## Крок 7. Що видно після відновлення

```bash
curl -s http://localhost:8080/observability
```

Очікується:

- `"fallback_events":3`, як у кроці 4: лічильник **кумулятивний і не спадає ніколи**;
- `"circuits":{"mock-mid":"closed","mock-mini":"closed","mock-strong":"closed"}`;
- `error_rate_pct` нижче за E1. Спад показує саме error rate: до дня додались два рядки `200`.

```bash
curl -s http://localhost:8080/providers
```

Очікується: усі три `"status":"ok"`. У консолі: «Fallback» — `3`, «Error rate» нижче, ніж у
кроці 4, три зелені точки провайдерів.

Рядки останніх запитів (найновіші першими):

```bash
docker compose exec postgres psql -U llmops -d llmops -c "SELECT created_at::time(0) AS at, model, status, prompt_tokens, latency_ms FROM requests ORDER BY created_at DESC LIMIT 5"
```

Очікується:

| Рядок | `model` | `status` | `prompt_tokens` |
|---|---|---|---|
| питання про замовлення | `mock-mid` | `200` | число > 0 |
| контрольне питання | `mock-mini` | `200` | число > 0 |
| три рядки інциденту | `mock-mini` | `503` | порожньо (`NULL`) |

**`prompt_tokens > 0` — доказ, що відповіла модель, а не кеш.** Cache-hit пише в токени `0`.
`latency_ms` для цього не годиться: hit у цьому сервісі триває кілька мілісекунд, а не рівно 0.

```bash
docker compose logs --since 3m service | grep -E "circuit|cache miss"
```

Очікується серед рядків:

- `circuit mock-mini half-open probe` і `circuit mock-mini closed after successful probe`;
- те саме для `mock-mid`;
- `cache miss for request …` — для обох питань кроку 6.

## Якщо щось пішло не так

| Симптом | Причина | Що робити |
|---|---|---|
| у кроці 2 `fallback_events` не `0` | пропущено крок 0, або між кроками 0 і 2 хтось надіслав `/chat` (чат у консолі, інший термінал) на ще холодний gateway: відмова з'єднання — це теж перемикання | крок 0, потім крок 1 до `200`, потім знову крок 2 |
| у кроці 3 відповідь не заглушка, а нормальна | у тексті немає `__fail_503` (зіпсовано копіюванням) | скопіюйте команду ще раз, дослівно |
| у кроці 6 знову заглушка | пауза коротша за 5 с: запобіжник ще відкритий, і модель пропущено без виклику | `sleep 6` і крок 6 ще раз (мітка часу дасть нове питання) |
| у кроці 6 «не знаю» замість відповіді про пароль | активний промпт `v1` | крок 1: активуйте `v2` |
| у кроці 7 `mock-mid` усе ще `open`, картка червона | питання про замовлення не надіслано, або надіслано раніше ніж через 5 с після інциденту | надішліть друге питання кроку 6 ще раз |
| у кроці 7 `error_rate_pct` дорівнює E1 | **мовчки, без помилки:** за день уже тисячі рядків, і спад ховається в округленні до 0,1 | точне значення з бази — запит нижче |
| `curl` нічого не друкує або `Connection refused` | стек не піднятий, або він на зсунутих портах | `docker compose ps`; для `demo-ports.yml` — таблиця портів вище |

Error rate з трьома знаками після коми (той самий вираз, що й у плитці):

```bash
docker compose exec postgres psql -U llmops -d llmops -c "SELECT count(*) AS requests, round(100.0 * count(*) FILTER (WHERE status <> '200') / NULLIF(count(*), 0), 3) AS error_rate_pct FROM requests WHERE created_at::date = CURRENT_DATE"
```
